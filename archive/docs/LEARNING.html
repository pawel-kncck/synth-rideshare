Concepts behind the grid simulation, one topic per tab.

The pyglet event loop

The event loop is what pyglet.app.run() starts at the bottom of main.py. It is an infinite loop that takes over the program and repeats three jobs until the window closes. Everything you write before run() is setup; nothing after it executes until the window is gone, because run() blocks.

What one iteration does

1. Process OS events Mouse, keyboard, resize, close. Each one is dispatched to a handler on the window.
2. Tick the clock Runs every callback whose scheduled interval has elapsed, passing it dt.
3. Redraw Calls on_draw on each window and flips the back buffer to the screen.
  1. Process OS events. pyglet asks the operating system for anything that happened since the last iteration. For each event it calls the matching handler on the window. The @window.event decorator on on_draw is how a handler gets registered. An on_key_press function registered the same way would be called at this point.
  2. Tick the clock. pyglet calls pyglet.clock.tick(), which checks every function registered with schedule_interval or schedule_once. Any whose interval has elapsed is called with dt, the real number of seconds since its last call. This is where the lambda that calls rider.pulse(dt) runs and updates the rider colours.
  3. Redraw. pyglet calls on_draw on each window, then swaps the freshly drawn back buffer onto the screen. In main.py the handler clears the window and draws the batch.

After those three steps the loop sleeps until the next scheduled callback or OS event is due, so it does not burn CPU spinning. In this program the next thing due is always the 1 / 60 second callback, so the result is a 60 Hz cycle of tick, redraw, sleep.

Why this shapes how you write the code

  • Setup, then hand over control. Create the window, shapes and riders first. Then call run() and let pyglet drive.
  • You never call on_draw yourself. You change state such as positions and colours, and the loop renders whatever the state is on the next redraw.
  • Handlers must return quickly. A time.sleep(1) or a long computation inside a handler or callback freezes the window, because the loop cannot reach its next iteration until your function returns.
  • One thread, fixed order. Input, updates and drawing always happen in the same sequence on the same thread, so there are no race conditions between them.

The loop, written by hand

pyglet.app.run() is a convenience. The same three steps can be spelled out explicitly, which is the most literal way to see what the loop does and to pause between iterations: 

while not window.has_exit:
    window.dispatch_events()          # 1. process OS events
    pyglet.clock.tick()               # 2. run due scheduled callbacks
    window.dispatch_event('on_draw')  # 3a. draw
    window.flip()                     # 3b. show the drawn frame
Stepping the simulation. Because Rider.pulse(dt) only needs a time delta, it does not have to be driven by the clock at all. Removing the schedule_interval line and calling pulse(1 / 60) for every rider from an on_key_press handler advances the simulation exactly one tick per key press, while the event loop keeps handling input and redrawing as normal.

Vocabulary

  • dt: delta time, the seconds elapsed since the previous call of that callback.
  • Handler: a function pyglet calls in response to an event, such as on_draw or on_key_press.
  • Scheduled callback: a function registered with the clock to run on a timer rather than in response to an event.
  • Back buffer: the off-screen image a frame is drawn into before being shown, so the user never sees a half-drawn frame.

schedule_interval and dt

This line in main.py is what makes the riders pulse: 

pyglet.clock.schedule_interval(lambda dt: [rider.pulse(dt) for rider in riders], 1 / 60)

It has three parts: a function to call, an interval to call it at, and the dt argument pyglet hands to the function each time.

schedule_interval(func, interval)

schedule_interval registers func with pyglet's clock. Nothing runs at that moment. Once pyglet.app.run() starts the event loop, the clock is ticked every iteration, and on each tick it checks whether at least interval seconds have passed since func was last called. If so, it calls func(dt).

  • The interval is a minimum, not a guarantee. With 1 / 60 pyglet aims for roughly 60 calls per second, but if a frame takes longer, the next call is simply late. It is never called early.
  • Missed calls are not stacked up. If the program stalls for half a second, you get one late call with a large dt, not thirty rapid calls.
  • Related functions. schedule_once(func, delay) calls once after a delay. schedule(func) calls on every loop iteration with no interval. unschedule(func) removes a registered function.
  • Extra arguments. Anything after the interval is passed through: schedule_interval(update, 1 / 60, riders) calls update(dt, riders).

What dt is

dt stands for delta time: the number of seconds, as a float, that actually elapsed since the previous call of this particular function. It is measured, not assumed. At a steady 60 Hz it will hover around 0.0167, but it wobbles from frame to frame and jumps when the machine is busy.

The key habit. Scale every change by dt instead of assuming one call equals one fixed slice of time. Then motion and animation run at the same speed in seconds regardless of how many frames the machine manages to produce.

Compare the two ways of advancing something:

# Frame based: speed depends on frame rate. Slow machine, slow animation.
self.elapsed += 1 / 60

# Time based: speed depends on wall time. Frame rate only affects smoothness.
self.elapsed += dt

Rider.pulse uses the second form. It accumulates dt into self.elapsed, then feeds that into a sine wave to compute a 0 to 1 blend between the base colour and the light colour. Because the input is elapsed seconds, the pulse completes exactly one cycle per second at any frame rate.

Why the callback takes dt even if it ignores it

pyglet always calls scheduled functions with dt as the first positional argument. A function that does not need it must still accept it, or the call fails with a TypeError. That is why the lambda is written lambda dt: ... rather than lambda: ....

The lambda and the list comprehension

lambda dt: [rider.pulse(dt) for rider in riders] is a one-line anonymous function. The list comprehension is used only as a compact loop. It builds a list of None values, one per rider, because pulse returns nothing, and that list is thrown away immediately. It works, but a named function says what it means more directly and costs nothing: 

def update(dt):
    for rider in riders:
        rider.pulse(dt)

pyglet.clock.schedule_interval(update, 1 / 60)

Fixed dt for stepping and testing

Because pulse only needs a number of seconds, you can call it yourself with a constant such as 1 / 60 and get identical results every run. The live clock passes a slightly different dt each frame, which is right for animation but not for reproducing a bug. When stepping the simulation by hand, use a fixed value.

Vocabulary

  • dt: delta time, measured seconds since the previous call of the same callback.
  • Interval: the minimum gap in seconds between calls, given as the second argument.
  • Frame based vs time based: advancing by a constant per call versus advancing by dt per call.
  • Hz: cycles per second. 1 / 60 seconds per call is 60 Hz.
