# Scenario 7 analysis: Service Reliability Hysteresis

- **Model identifier:** `grok-review-07` (Grok / xAI-based review agent; exact underlying model build string unavailable to this subagent)
- **Review date:** 2026-09-09 (Europe/Warsaw)
- **Repository revision inspected:** `main` @ `28e839eae51358d7646ae0a5f156508ba30b1c11`
- **Method:** Independent inspection via GitHub MCP (`get_file_contents`) of scenario inputs and simulator modules; no full scenario run executed. Assessment is based on code and architecture docs, not other models' reports.

### 1. What is currently possible

Several building blocks for a *soft* reliability-and-preference experiment exist today, but they do not implement the DESCRIPTION's hard hysteresis state machine.

**Two-platform market, population sizes, horizon, and tariffs.** A scenario can start from `three-platform-week@1` / `three-platform-day@1` in `scenario.py` (`_three_platform_week_v1`, `_three_platform_day_v1`) and override `world.horizon_hours` (e.g. 120), `population.riders.count` (200), and `population.drivers.count` (35). Platform commercial terms are configurable via `platforms.<id>.policy.parameters` (`base_fare_minor`, `per_km_minor` in `marketplace_policy.py` / `MarketplaceParameters`). With `world.minor_units_per_major` default 100, Budget ≈ `base_fare_minor=100`, `per_km_minor=100` and Reliable ≈ `300` / `180` maps to the DESCRIPTION's $1+$1/unit vs $3+$1.80/unit under a km-as-unit assumption. Flyt can be left unused (`launched=False` and/or removed from segment `apps`) while Rebu/Blot stand in for Budget/Reliable.

**Rider starting preference for the cheap platform + dual installs.** `PersonProfile.preferred_app` and segment/`person(...)` builders in `scenario.py` (`segment`, `person`) set initial preferred apps and installed `apps`. Riders can install both platforms with `preferred_app` on Budget. Driver exclusivity vs multihoming is expressible the same way (`apps` / `registrations`): e.g. 25 Reliable-only drivers and 10 dual-app drivers.

**Supply timing that approximates Phase 1 scarcity and Phase 2 recovery.** Population is fixed at `Plan.prepare`, but exogenous `activity.shifts` can be `explicit` (`shift(...)` in `scenario.py`). Budget-exclusive drivers can remain offline until `at_hours=48`, which is the supported way to "inject" supply without a mid-run population mutation. Phase 1 wait/cancellation *rates* then emerge from sparse Budget supply interacting with `MarketplacePolicy.dispatch` (`order_patience_seconds`, `max_attempts`) and rider `cancellation_after_seconds` (default 600s in `RiderTraits`), not from authored targets of ">12 minutes" / ">30%".

**Persistent preferred-app memory across days (partial answer to the modeling challenge).** Per-person runtime state in `policy_runtime.py` stores `preferred_app` and `scores` across the run and through `Simulation.snapshot` / `restore`. `RiderPolicy.decide` always opens the preferred usable app first (`OpenApp(first)` when `visited` is empty) and adds `loyalty * (p == preferred_app)` in purchase utility. So brand affinity is **not** purely tick-stateless: preferred app and learned scores persist. Trip **search** memory (`visited`, `attempts`, …) is per-intent and resets each trip.

**Soft switching via learning (not the Fatigue Rule).** If `behavior.evolution.parameters.learning_rate > 0` and checkpoints are scheduled (`evolution.checkpoint_hours`), `EvolutionPolicy.checkpoint` updates scores from `context.observations` and may change `preferred_app` when a candidate beats the current preferred by `preference_margin` after `preference_cooldown_seconds` (`EvolutionTraits`, default cooldown 86400s). Cancellations feed `add_reward(..., -1, 'cancellation', ...)` from `order_canceled` in `policy_runtime.py`; completions use `rider_reward` (wait and ETA error penalties). Exogenous `preference_change` interventions (`scenario.preference_change`) can also force preferred apps for a segment/people list at a given time.

**Observability for market outcomes (partial).** Raw `simulation.log` retains quotes, orders, cancellations, policy decisions, `personal_reward` observations, interventions, and boundary checkpoints including `preferred_app` / scores. Offline `metrics.calculate_metrics` reports `average_order_to_pickup_seconds`, cancellation/completion counts, and `platform_completion_share_pct`; `--market-share-days 1` yields daily completion shares via `aggregate_market_share`. Installs (apps) live in population/checkpoint state and are **not** the same metric as completion share—docs in `metrics.py` explicitly say market share uses completions, not installation counts. First-choice *query* volume by preferred platform is reconstructible from logs/notifications (quote requests / `OpenApp` decisions) but is not a first-class metrics field.

**Limits.** Default `learning_rate=0` freezes preference learning. There is no guarantee Phase 1 hits the DESCRIPTION's wait/cancel thresholds or that Phase 2 average ETA is 4 minutes—those are emergent. Utility-based inspection can still send converted riders to Budget when Reliable looks expensive (`inspect_probability` from price/ETA excess in `RiderPolicy.decide`), so "first-choice" sticky behavior is soft.

### 2. What is almost possible with a small, quick, independent adjustment

**Consecutive Budget failure counter + Fatigue Rule (localized rider/evolution change).** Gap: neither `RiderPolicy` intent memory nor `EvolutionPolicy` JSON memory declares a consecutive-failure counter; nothing implements "two consecutive failed trips on Budget ⇒ switch preferred to Reliable." Smallest adjustment: extend rider or evolution memory with e.g. `budget_consecutive_failures`, increment on Budget `order_canceled` (and optionally on completed trips whose pickup wait exceeds a configurable threshold), reset on successful Budget completion under threshold, and set `preferred_app` to Reliable when the counter reaches 2—either immediately in `policy_runtime.on_notification` or inside `EvolutionPolicy.checkpoint` / a new lightweight hook. Affected surfaces: `behavior_policy.py` (`RiderPolicy` / `EvolutionPolicy` declaration memory schema), `policy_runtime.py` (`add_reward` / `order_canceled` / `order_completed` paths), optionally a new `RiderTraits` or `EvolutionTraits` parameter for the threshold. Independent of marketplace matching. Verify with a tiny explicit fixture (few riders/drivers, forced cancels) and assert preferred-app transitions in the final checkpoint / decision log.

**Treat long pickup waits as failures without cancellation.** Gap: DESCRIPTION counts wait > 12 minutes as failure even if the ride completes; today long waits only reduce `rider_reward` continuously. Small adjustment: in `policy_runtime` completion handling (or `rider_reward` callers), if `arrived - created_at` exceeds a configurable seconds threshold, emit a failure-tagged observation or bump the consecutive-failure counter. Touches one notification path plus a trait default (e.g. 720). Verify by scripting a slow pickup and checking the counter/observation.

**Hysteresis lock (no automatic revert).** Gap: with learning enabled, improved Budget waits in Phase 2 can raise Budget scores and switch preferred back after cooldown—contradicting "do not automatically revert … unless Reliable fails them." Small adjustment: a sticky flag (e.g. `abandoned_budget=True`) set by the Fatigue Rule that blocks Budget from winning `preferred_app` in `EvolutionPolicy.checkpoint` unless Reliable produces failures or an explicit `preference_change` / campaign intervention runs. Verification: Phase-2-only improvement of Budget supply should leave the converted cohort's `preferred_app` on Reliable.

**Metrics for installs vs daily first-choice query volume.** Gap: completion share exists; "daily active query volume" vs 100% dual installs does not. Small offline extension in `metrics.py` to count per-day, per-platform quote requests or preferred-app opens from the log, plus install counts from the initial state—no engine change. Verify against a known dual-install population with skewed preferred apps.

### 3. What is not currently possible and what must be developed

**True individual hysteresis state machines as specified.** The simulator has persistent `preferred_app` and learned scores, but **not** per-rider consecutive failure counters, **not** an automatic two-strike Budget→Reliable transition, and **not** a non-reversion lock. Approximating with high `learning_rate`, low `preference_margin`, and tuned rewards loses: (a) exact two-strike discreteness, (b) failure definition including completed-but-slow trips, (c) guaranteed non-reversion when Budget recovers, (d) independence from checkpoint cadence. Delivering the DESCRIPTION faithfully needs the Section 2 counter/lock (or a custom registered rider/evolution policy with the same semantics) plus scenario parameters for thresholds.

**Hard Phase 1/2 service-level guarantees.** There is no scenario knob for "cancellation rate exceeds 30%" or "average wait = 4 minutes." Supply interventions cannot add people mid-run—only shift schedules and policy/preference/launch interventions (`policy_runtime._intervene`: launch, policy compile replace, preferred_app). Achieving the DESCRIPTION's numerical service targets requires either iterative calibration of counts/geography/speeds or new exogenous reliability controls (e.g. forced cancel/delay injectors)—the latter is a new capability, not a quick trait tweak.

**Push-notification courting as a first-class return path.** DESCRIPTION allows return only if Reliable fails or Budget "actively courts them with a push notification (which does not occur)." Announced campaigns (`awareness='announced'`) affect discovery ranking via `context.announced`, and `preference_change` can force preference, but there is no rider push-notification object that specifically re-courts abandoned users. Modeling that return channel needs new intervention/behavior surface area if it becomes in-scope later.

**Stateless-every-tick vs permanent affinity—unresolved without the Fatigue Rule.** Main modeling challenge: today decisions mix **persistent** preferred/scores with **per-intent** utility draws. Without the hard rule, Phase 2 can erode abandonment through price-driven inspection and learning. The DESCRIPTION's intended mechanism (permanent brand abandonment after two strikes) is therefore an **undeveloped requirement**, not merely an untuned preset.

### 4. Documentation quality and code readability

**What helped.** Root `README.md` clearly maps modules and the scenario compile/prepare/run loop. `plans/architecture/behavior-policy.md` is the strongest guide: it documents preferred-app persistence, checkpoint ordering (interventions → snapshot → learning/adoption), `preference_margin` / cooldown, cancellation rewards, and explicitly states learning rate zero freezes preferences. `plans/architecture/scenario-definition.md` documents interventions, population segments, and that population/activity are fixed exogenous inputs. Typed builders (`preference_change`, `person`, `shift`, `campaign`) and example scripts under `scenarios/` (e.g. `fixture_cross_platform_queue.py`, `flyt_growth_month.py`) make configuration discoverable.

**Gaps / misleading edges for this scenario.** No doc names "hysteresis," "consecutive failures," or "fatigue." A reader could over-read "learned preference" / loyalty as satisfying Scenario 7's hard state machine. Market-share docs correctly stress completions ≠ installs, but do not explain how to measure first-choice query volume vs install base—the DESCRIPTION's fourth check. Phase-style supply injection via delayed explicit shifts is inferable from activity docs but not presented as the supported substitute for "inject drivers at t=48."

**Code readability.** `behavior_policy.py` is compact and the preference-switch block in `EvolutionPolicy.checkpoint` is easy to audit; `policy_runtime.py` reward wiring on `order_canceled` / `order_completed` is clear. Confidence is high that no hidden consecutive-failure counter exists elsewhere: rider intent memory fields are declared on `RiderPolicy.declaration`, and evolution memory fields on `EvolutionPolicy.declaration`. Actionable suggestions: (1) add a short "scenario coverage" note under behavior docs listing unsupported mechanisms (consecutive failure hysteresis, SLA injectors); (2) document delayed explicit shifts as the supply-shock pattern; (3) extend metrics docs with an example of reconstructing preferred-app query share from logs.
