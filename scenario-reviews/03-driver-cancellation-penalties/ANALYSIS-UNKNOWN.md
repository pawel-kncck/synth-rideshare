## 1. What is currently possible

Several structural pieces of the scenario can already be expressed with configuration and existing engine/policy surfaces.

**Two platforms with asymmetric commercial rules on one shared physical market.** Presets and the scenario compiler support multiple platforms (`scenario.py` platform table / `_base_v1`, `Plan.platforms`). Drivers and riders can install and open multiple apps (`Driver.apps` / `open_apps`, `Rider.apps` / `open_apps` in `marketplace_engine.py`). Multihoming drivers with accounts on both “Strict” and “Lenient” stand-ins (e.g. `rebu` / `blot`) are therefore in scope without code changes. Physical motion, commitments, and service remain engine-owned and shared (`marketplace_engine.py`), which already matches the modeling challenge’s “do not disconnect from the global physical world” half of the requirement for ordinary cancel/open/close flows.

**Population size, horizon, and fare/take-rate knobs.** `population.riders.count` / `population.drivers.count` and `world.horizon_hours` are scenario fields (`scenario.py`). Platform tariff parameters include `base_fare_minor`, `per_km_minor`, and `commission_fraction` (`marketplace_policy.py` `PlatformParameters`, defaults bound in `scenario.py` around the `_platform_v1` defaults). Mapping the scenario’s $2.50 base, $1.20 per unit, and 15% take-rate is straightforward if a “unit” is treated as a map kilometre (`per_km_minor`) and money uses `minor_units_per_major` (default 100). Example overrides: `base_fare_minor=250`, `per_km_minor=120`, `commission_fraction=0.15`. World geometry defaults to a 10×10 km map with `grid_step_km=1` (`scenario.py` `_base_v1`).

**Pre-boarding cancellations by rider or driver.** The engine’s `cancel_order` (`marketplace_engine.py`) accepts `by` in `CANCELLATION_PARTIES = ("rider", "driver", "platform")`, rejects cancel after boarding/transport, records `order.cancellation = {"by", "reason"}`, releases only that commitment, and notifies parties. Rider patience before cancel is `RiderTraits.cancellation_after_seconds` (default 600 s ≈ 10 minutes) in `behavior_policy.py` / `RiderPolicy.progress`. Driver post-accept cancel uses `DriverTraits.cancel_after_seconds` (default 7200 s) in `DriverPolicy.progress` (“commitment patience exhausted”). Both paths go through `policy_runtime.py` `cancel`, which asks the platform `MarketplacePolicy.cancel` then calls `engine.cancel_order`.

**Rider-side cancellation money (not the scenario’s driver dock).** `PlatformParameters.rider_cancellation_fee_minor` and `driver_cancellation_compensation_minor` feed `MarketplacePolicy.cancel`, which applies those amounts **only when `context.party == "rider"`**; driver/platform requests get zero fees (`marketplace_policy.py`; documented in `plans/architecture/marketplace-policy.md`). Settlements use reason `"cancellation_fee"` (`Settlement` in `marketplace_engine.py`). So Lenient vs Strict can differ on **rider** cancel fees today; that does **not** implement docking the driver’s accrued balance on **driver** cancel.

**Partial observability for the listed trip metrics.** Offline `metrics.py` reconstructs offer disposition counters (`accepted_offers`, `canceled_offers`, …), `canceled_orders`, completions, and aggregated `cancellation_settlements` from the structured log / initial–final state. Engine state retains per-order `timeline`, `assignment.accepted_at`, and `cancellation.by`. Distinct named summary metrics for “Dispatched,” “Accepted,” “Driver Cancelled,” “Rider Cancelled,” and “Completed” as separate first-class series are **not** emitted; see sections 2–3. Offer/dispatch attempts are visible via order `offer_ids` and offer records.

**Asymmetric app presence without leaving the world.** Closing one platform app (`close_app` / `ExpandApps.close_apps` in `marketplace_engine.py` / `policy_runtime.py`) stops `_driver_accepting` for that platform only while other open apps remain eligible. That is a voluntary/search-policy mechanism, not an automatic penalty lockout, but it shows the engine already supports platform-scoped eligibility without removing the driver from the physical simulation.

## 2. What is almost possible with a small, quick, independent adjustment

These gaps look localized: extend existing cancel/settlement or metric aggregation without a new subsystem.

**Charge the driver on driver-initiated cancel (approximation of the $4 dock).** Today `Cancel` only carries `rider_fee_minor` and `driver_compensation_minor` (`policy_contracts.py`), and `cancel_order` settles those as rider payment / driver payout with nonnegative `minor_units` (minimum 0). Docs state driver/platform cancels have zero fees. A small change could add something like `driver_penalty_minor` (or allow a signed driver leg on `cancellation_fee` settlements) wired from `PlatformParameters` through `MarketplacePolicy.cancel` when `party == "driver"`, and apply it in `cancel_order` / `_settle`. Affected surfaces: `policy_contracts.py`, `marketplace_policy.py`, `marketplace_engine.py`, `policy_runtime.py` cancel path, and architecture notes in `plans/architecture/marketplace-policy.md`. Verification: unit-style throwaway script canceling an accepted order as driver and asserting a settlement of 400 minor units against the driver (and none when Lenient params are 0). **Caveat:** there is still no persistent “accrued ledger balance” object (section 3); a settlement line is the nearest existing money record.

**Split canceled-order metrics by `cancellation.by`.** `calculate_metrics` already loads canceled orders via `_new_terminal(..., "canceled")` but only reports `canceled_orders` as a count. Adding `driver_canceled_orders` / `rider_canceled_orders` / `platform_canceled_orders` (and optionally platform breakdowns) from `order["cancellation"]["by"]` in `metrics.py` would make the scenario’s “Driver Cancelled” vs “Rider Cancelled” checks first-class without changing the engine. “Dispatched” / “Accepted” could similarly be derived from offer states and `assignment` presence. Verification: rebuild metrics from an existing `simulation.log` and compare counts to manual JSON inspection of orders.

**Tune driver cancel timing toward a 6-minute post-accept horizon.** Setting `behavior.driver.parameters.cancel_after_seconds` to `360` makes drivers request cancel after six minutes of unboarded commitment (`DriverPolicy.progress`). That approximates “long pickup ⇒ cancel” in time, but **not** “cancel iff displayed/private ETA > 6 minutes when penalties are absent,” and it does not weigh a $4 fine vs completing the pickup. Still useful for Strict vs Lenient A/B on patience alone once financial/lockout rules exist.

**Configure Strict vs Lenient parameter packs.** Two platform policy versions/parameter blocks with different cancel-related fields (once driver penalty / lockout fields exist) fit the existing versioned `PlatformPolicy` / `with_changes` / `policy_change` authoring model (`scenario.py`, README examples). No architectural blocker for dual-platform experiments once the missing mechanisms exist.

## 3. What is not currently possible and what must be developed

**Stateful driver account balance with penalty docks.** Drivers have `accounts` as platform membership sets, not monetary ledgers (`Driver` in `marketplace_engine.py`). Money appears as discrete `Settlement` rows (completed rides or cancellation fees), not a running accrued balance that can be decremented by $4 and inspected mid-run. Scenario checks that “every driver cancellation on Platform Strict results in an immediate $4.00 deduction from the driver’s ledger balance” require new balance/ledger state (or an explicit cumulative view over settlements) plus write paths on driver cancel. Success check: after Strict driver cancel, balance decreases by 400 minor units; Lenient cancel leaves balance unchanged; rider cancel does not debit the driver.

**Asymmetric platform-level temporary dispatch lockout (30 simulation minutes).** There is no penalty timer, ban list, or dispatch filter keyed by “this driver may not receive offers from platform X until time T.” Candidate selection in `MarketplacePolicy.candidates` filters on `accepting`, pending offers, and local commitment caps—not penalty lockouts. Closing an app is not an automatic, timed, cancel-triggered Strict-only ban; behavior policies do not schedule a 30-minute reopen after a fine. Needed: platform (or runtime) memory of lockout-until timestamps set on driver cancel under Strict params, consulted in dispatch/candidate eligibility (and possibly offer acceptance), while leaving other platforms’ eligibility intact. Success check: during Strict lockout, Strict offers are not issued (or are rejected), Lenient offers still work, and eligibility restores after 0.5 hours.

**Driver decision policy that cancels based on pickup ETA when penalties are absent, and weighs fines/lockouts when present.** Current `DriverPolicy.respond` uses a logistic of payout, private ETA, loyalty, and scores; it hard-rejects only if `private_eta_seconds > max_private_pickup_seconds` (default 3600 s). Post-accept cancel is purely elapsed-time patience (`cancel_after_seconds`), not “ETA > 6 minutes and cancel is free.” There is no trait for a 4-unit acceptance radius (dispatch ranks by distance/ETA among open accepting drivers; acceptance is probabilistic). Reproducing the described Strict tradeoff (unprofitable long pickup vs $4 + lockout) needs behavior (and observations) that know penalty terms and lockout state—likely new traits, cancel-hook inputs, and documentation in `plans/architecture/behavior-policy.md`.

**First-class metric names exactly as specified.** Without metric or logging extensions, “Dispatched / Accepted / Driver Cancelled / Rider Cancelled / Completed” are only partially recoverable: completions and aggregate cancels exist; party-split cancels and a clear “Dispatched” counter do not. Log forensics can approximate some checks (`order.cancellation.by`, offer states) but that is not the same as recorded distinct metrics.

**Named Platform Strict / Lenient presets for this experiment.** No scenario package under `scenario-reviews/03-...` configures the run; reviewers must author a `Scenario` themselves. That is authoring work, not a capability gap, once mechanisms exist.

## 4. Documentation quality and code readability

**What helped.** The root `README.md` maps files to responsibilities and shows the `Scenario` / `compile_scenario` / `run_scenario` authoring loop. `plans/architecture/marketplace-policy.md` explicitly documents that rider cancellation fees/compensation apply to rider requests and that driver/platform cancels have zero fees—directly useful for ruling out the $4 driver dock. `plans/architecture/behavior-policy.md` documents `cancellation_after_seconds`, `cancel_after_seconds`, multihoming expansion, and private vs displayed ETA. Reading `MarketplacePolicy.cancel`, `cancel_order`, and `DriverPolicy.progress` side-by-side made the cancel money path and patience semantics clear. Typed dataclasses (`Cancel`, `Settlement`, `PlatformParameters`) are readable and citeable.

**What hurt or scattered.** Cancellation economics, dispatch eligibility, and behavior patience are split across `marketplace_policy.py`, `marketplace_engine.py`, `behavior_policy.py`, `policy_runtime.py`, and two architecture docs; there is no single “cancellation penalties” index. The scenario’s “ledger balance” and “dispatch lockout” vocabulary does not appear in docs or code, so absence had to be inferred by search rather than an explicit limitation list. `metrics.py` documents reconstruction rules well for completions and offer dispositions, but does not mention filtering cancels by party. Scenario “units” vs simulator kilometres / minor currency units need an explicit mapping note for reviewers. No unit test suite (README) lowers confidence that edge cases (driver cancel after assignment but before arrive; cross-platform open apps during a hypothetical ban) are locked in.

**Actionable suggestions.** (1) Document in marketplace-policy that driver-initiated cancel currently cannot levy driver penalties or lockouts, and point to the exact parameters that *do* exist for rider cancel. (2) Add a short “observability” subsection listing how to derive cancel-by-party from logs until metrics grow those fields. (3) Cross-link behavior-policy driver cancel patience to marketplace cancel fee rules so Strict/Lenient experiments are harder to misconfigure. (4) Keep symbols such as `rider_cancellation_fee_minor` vs a future `driver_cancellation_penalty_minor` clearly named to avoid conflating compensation with docks.

---

**Bottom line:** The simulator can already host a dual-platform, multihoming, pre-boarding cancel experiment with configurable fares, take-rates, populations, and rider wait-to-cancel. It does **not** yet support the scenario’s core Strict mechanisms—driver balance docks, timed Strict-only dispatch lockouts, or ETA/penalty-aware driver cancel choice—nor first-class party-split cancel metrics. Small extensions could add driver-cancel settlements and metric splits; ledger + lockout + decision policy are larger capability gaps.
